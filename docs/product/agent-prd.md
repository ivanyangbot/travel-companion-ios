# 旅行 Agent MRD

- 文档版本：v1.1

## 1. 产品定义

帮助用户把“想去哪里、看过什么攻略、花了多少钱、明天要准备什么”转成可检查、可选择、可落地的旅行行动。

具体实现路径是，把外链、多模态输入等，转为**结构化**的本地数据，并持久存储、展示用户的行程。

## 2. 功能范围

| 能力 | 用户可完成的事 | 最终落地前的确认 |
| --- | --- | --- |
| 行程规划 | 用对话、攻略图、外部链接补齐某天或某个时段的行程 | 勾选每张候选卡后加入行程 |
| 攻略整理 | 将公开攻略链接整理成一或多张待编辑的行程卡 | 检查并补充信息后保存 |
| 单卡录入 | 通过补问创建/修改/删除一张活动、酒店或航班卡 | 草案完整后确认保存 |
| 支出录入 | 用小票或自然语言等生成一笔实际支出 | 预览、修改、选择关联卡后保存 |
| 卡包识别 | 从卡片照片提取标签、号码、备注和类型 | 用户检查后保存到本机卡包 |
| 明日备忘 | **自动**根据次日安排生成闹钟、提醒与物品清单 | 单条或全部添加 |

### 不做的事

- 不自动删除、替换或调整已保存的行程。
- Agent本身不生成具体的 POI 地理信息，通过服务端 Apple Map 服务获取信息并录入。
- 生成卡片时，不生成实际价格字段；录入价格时，确认前不录入实际价格字段。
- 不把未确认的候选、草稿文本和攻略图片共享给同行人。
- 不把卡包中的号码、证件和备注作为旅行规划上下文。

### 服务端/用户端 Tools  (For ref only)

- map-search-tool: 通过服务端 Apple Map 服务获取信息，应考虑同步/异步调用以防止AI流式输出被阻断。只用于POI搜索，不用于查找景点等。例如使用该工具搜索“朝阳区景点”的操作不符合预期。
- card-write-tool：应保障卡片内部能及时读取不同字段的标签并以正确的ui输出，可考虑json/XML等标注不同字段。核心是**持续流式输出，不等待标签结束**、**标签未完全读取时，应当尽量缩短用户注意到未正确渲染文本的时间**。
- web-search-tool：由LLM提供方提供，应用于保障行程建议，例如联网查找“雍和宫citywalk指南”。

## 3. 共同体验规则

1. 先建议，后写入。
2. **严禁写入** “在附近的景点闲逛” “在北京市的酒店休息” 等无具体信息的卡片。
3. 局部操作优先，失败不丢内容。
4. 严禁将 “北京市全季酒店” 这种不经过服务端 Apple Map 服务直接被写入地址的字段。

### 3.1 当前行程字段与格式

本节是当前 App 的行程数据口径。行程规划、攻略导入、手工新建和编辑卡片都使用同一套字段；Agent 生成的内容只能预填这些字段，不能凭空新增字段。

#### 旅行基本信息

| 字段 | 格式 | 示例 | 规则 |
| --- | --- | --- | --- |
| 目的地 | 1–120 个字符 | `东京`、`巴厘岛` | 必填，作为整趟旅行和地点搜索范围 |
| 出发日期 | `YYYY-MM-DD` | `2026-10-01` | 必填，不能晚于返程日期 |
| 返程日期 | `YYYY-MM-DD` | `2026-10-05` | 必填，与出发日期共同定义可排期范围 |
| 旅行货币 | 3 位大写货币代码 | `CNY`等 | 必填；全程采用一个主要货币，已有支出后不可更改 |

#### 日期与排序

| 字段 | 格式 | 示例 | 规则 |
| --- | --- | --- | --- |
| 行程日期 | `YYYY-MM-DD` | `2026-10-02` | 必须落在旅行日期范围内；同一日期只保留一个日期分组 |
| 日期顺序 | 按日期升序 | 10 月 1 日 → 10 月 2 日 | 用于时间轴展示 |
| 卡片顺序 | 同日内的顺序号 | 上午活动 → 午餐 → 下午活动 | 默认按开始时间阅读，用户可上移、下移调整 |

#### 行程卡片通用字段

| 字段 | 格式 | 示例 | 规则与展示 |
| --- | --- | --- | --- |
| 卡片类型 | `机票` / `酒店` / `活动` | `活动` | 必填；决定图标和专属字段 |
| 标题 | 1–160 个字符 | `故宫博物院游览` | 必填；活动标题写活动本身，不重复地点名称 |
| 开始时间 | 带日期的时间 | `2026-10-02 09:30` | 必填；作为时间轴定位依据 |
| 结束时间 | 带日期的时间 | `2026-10-02 12:00` | 必填；不得早于开始时间，未填时仅显示开始时间 |
| 地点 | 具体地点名称 | `故宫博物院` | 必填；酒店、活动优先填写可定位的具体地点 |
| 简介 | 最多 2,000 个字符 | `皇家宫殿建筑群，适合上午游览。` | 必填；展示亮点与适合人群 |
| 备注 | 最多 2,000 个字符 | `建议提前预约，避开周一。` | 必填；记录预约、排队、交通、集合等信息 |
| 公开链接 | HTTPS 链接 | 景点介绍或攻略页 | 必填；可打开、分享，不填写私有账号链接 |
| 图片 | 最多 8 张，按添加顺序排列 | 封面图 + 攻略图 | 必填；第一张为封面，其余用于详情轮播 |

#### 地点字段

| 字段 | 格式 | 示例 | 规则与用途 |
| --- | --- | --- | --- |
| 地点名称 | 1–160 个字符 | `浅草寺` | 卡片和地图的主要展示字段 |
| 地址 | 最多 500 个字符 | `东京都台东区浅草 2-3-1` | 展示在地点名称下方，可一键复制 |
| 地理位置 | 经纬度同时存在 | 纬度 `35.7148`、经度 `139.7967` | 有位置时才能使用地图打开和路线规划；没有位置禁止文字地点保存 |
| 城市/地点标识 | 搜索结果附带的信息 | 同名“万达广场”的具体城市标识 | 用于区分同名地点，用户通常不需要编辑 |

活动和酒店由 Agent 生成时，地点必须是具体、可定位的实体；“市中心酒店”“夜市逛逛”“自由活动”只能作为用户意图，不能直接写入地点字段。

#### 类型专属字段

| 类型 | 字段 | 格式 | 规则与展示 |
| --- | --- | --- | --- |
| 机票 | 出发机场、到达机场 | 文本，例如 `HND` → `KIX` | 两者同时填写时显示为航线；每项最多 160 个字符 |
| 机票 | 订单号/航班号 | 文本，例如 `JL123` | 必填，最多 128 个字符；可一键复制 |
| 酒店 | 入住/退房时间 | 使用开始时间和结束时间 | 建议填写结束时间，明确住宿区间 |
| 活动 | 门票价格 | 旅行货币金额，例如 `60.00 CNY`、`600 JPY` | 必填；独立于预估价和实际价展示 |
| 活动 | 预计停留 | 正整数分钟，例如 `90` | 必填；显示为“1 小时 30 分钟”，范围为 1–100,000 分钟 |
| 活动 | 游玩提示 | 最多 10 条、每条最多 500 字符 | 必填；按顺序展示，例如“提前预约”“穿舒适鞋” |

#### 价格字段与显示格式

| 字段 | 格式 | 示例 | 展示规则 |
| --- | --- | --- | --- |
| 预估价 | 大于 0 的旅行货币金额 | `60.00 CNY`、`600 JPY` | 计划阶段的参考成本，不代表已付款 |
| 实际价 | 大于 0 的旅行货币金额 | `58.00 CNY` | 填写后优先展示，替代卡片上的预估价 |
| 门票价格 | 大于 0 的旅行货币金额 | `40.00 CNY` | 活动专属成本，与预估价、实际价分开显示 |

用户以常见货币格式输入金额。两位小数货币如人民币显示 `60.00 CNY`；日元、韩元、越南盾等无小数货币显示为整数，如 `600 JPY`。

#### Agent 候选卡的字段要求

| 候选信息 | 加入行程后的字段 | 用户确认重点 |
| --- | --- | --- |
| 建议日期与时间 | 行程日期、开始时间、结束时间 | 是否与已有安排冲突，是否需要调整时段 |
| 建议地点与地址 | 地点名称、地址、地理位置 | 是否是用户要去的具体地点 |
| 推荐理由与提示 | 简介、备注、游玩提示 | 是否保留，需要补充哪些预约或交通信息 |
| 参考价格 | 预估价或门票价格 | 只作预算参考，不能当作成交价格 |
| 航班信息 | 出发机场、到达机场、订单号/航班号 | 必须以用户订单为准 |

用户确认加入前，Agent 候选至少要具备：卡片类型、标题、所属日期和开始时间。活动、酒店缺少具体地点时，必须保持为“待确认”，不能默认写入行程。

## 4. 行程规划 Agent

### 4.1 目标体验

行程规划页是“计划工作台”，提供本地存储的聊天记录。用户用对话表达想法，结果以按日时间轴和候选卡呈现；用户能一眼看出：去哪、什么时候去、为什么推荐、是否可信、预计花多少钱、还要确认什么。在用户表达清晰想去的具体地点时，应该完全遵循用户指令，并补齐对应行程缺少的字段；除了实际价格，不应有任何字段被留空（如果用户已经告诉agent实际价格，则任何字段不应被留空）。

### 4.2 首次进入

首屏提供可组合的条件，用户可以设置以下条件组（持久存储，每次对话都给agent发送作为前置条件）。

| 条件组 | 示例选项 | 对用户意味着什么 |
| --- | --- | --- |
| 旅行节奏 | 轻松、均衡、特种兵 | 控制每天安排的密度和开始时间 |
| 同行人 | 独自、情侣、带父母、带儿童 | 调整步行、休息、无障碍和夜间活动建议 |
| 预算 | 省钱、适中、品质优先 | 改变候选优先级，价格始终只是参考 |
| 偏好 | 美食、文化、自然、购物、拍照、夜生活 | 让推荐更贴近兴趣 |
| 本轮范围 | 补今天、补某一天、规划空白日、只找住宿/餐厅 | 明确本次只处理的日期或卡片类型 |

并提供可一键发送的示例：

- “帮我安排明天，带父母、少走路。”
- “第二天下午换成室内活动。”
- “按人均 500 元补齐空白日。”
- “根据这几张攻略图整理必去点。”

当信息不足以给出具体建议时，助手最多询问两个真正影响结果的问题，例如“住在哪个区域？”或“是否有必须保留的预约？”。不连续追问泛化问题。

### 4.3 结果工作台

每轮结果都在聊天内容中形成“本轮建议”工作台。

| 区块 | 用户看到什么 | 可以做什么 |
| --- | --- | --- |
| 本轮摘要 | 覆盖日期、采用条件、生成了哪些建议、哪些事项待确认 | 点击条件继续修改 |
| 按日时间轴 | 已保存行程与新增候选的前后关系、空档和时间冲突 | 切换“只看新增 / 与当前行程对比” |
| 候选卡 | 时间、地点、地址、推荐理由、参考价格、实用提示、验证状态 | 勾选、取消、查看地图、要求替换、查看详情 |
| 变更清单 | 本轮将新增的项目；出现调整时还应列出替换和移除项 | 逐项确认后加入行程 |

默认一次展示不超过 6 张候选卡、单日不超过 3 张；其余结果收起为“查看其余 n 项”。优先展示最符合条件、地点最明确、与已有行程冲突最少的候选。

候选卡的信息顺序固定为：

1. 地点与时段：标题、日期/时间、地点、地址、地图入口。
2. 推荐理由：用一句话说明它为何符合本次条件。
3. 执行成本：参考价、预计停留、前后安排的交通成本；不知道时写“待确认”。
4. 风险与待办：预约、闭馆日、排队、营业时间、无障碍等。
5. 可信度标识：`地点已验证`、`地点待确认`、`价格仅参考`、`需预约`。

### 4.4 行程规划的典型用户旅程

#### 旅程 A：带父母的城市一日游

**用户背景**：小林和父母去东京，第二天没有安排，但父母不适合长时间步行。

1. 小林打开行程规划，选中“带父母”“轻松”“补某一天”。
2. 输入：“安排明天，从浅草附近出发，想看一个经典景点，再找一家安静的午餐。”
3. 助手只追问一次：“是否需要避开楼梯或长距离换乘？”小林选择“尽量少走路”。
4. 工作台给出上午景点、午餐和下午休息/室内备选；每张卡显示地点、推荐原因、预计停留和“需预约/待确认”提示。
5. 小林勾选上午景点和午餐，取消下午活动，点击“加入行程（2）”。
6. 行程时间轴出现两张新卡；同行人下一次查看行程时只看到已加入的两项。

**成功标准**：小林不需要切换多个 App 搜索地点，也不用手动录入卡片的基础信息；最终只加入自己认可的两项。

#### 旅程 B：把攻略截图变成可执行计划

**用户背景**：阿曼从社交平台保存了 3 张巴厘岛攻略图，想挑出适合自己的点，而不是照搬整篇攻略。

1. 阿曼在行程规划页上传 3 张图片，选中“拍照”“均衡”“规划空白日”。
2. 输入：“这是我收藏的点，帮我挑最值得去的，别排得太满。”
3. 助手在结果摘要中说明识别到的主题，并将可落地的地点做成候选卡；无法确定地点的内容显示“地点待确认”，不混进已验证候选。
4. 阿曼看到每张卡的“为什么推荐”，保留两个海边点，选择“换室内”让助手补一个雨天备选。
5. 阿曼只导入三张卡；原攻略图片和未导入候选仍只停留在本次草稿中。

**成功标准**：用户从“收藏很多、不会取舍”变成“得到一个可执行且留有余量的日程”。

#### 旅程 C：下雨后的局部替换

**用户背景**：小周原计划下午去户外景点，天气变化后希望改为室内，但不想影响晚餐和已经约好的演出。

1. 小周在当天时间轴点击下午的活动卡，选择“换室内”。
2. 页面明确显示影响范围：“只调整 14:00–17:30，不影响晚餐和演出。”
3. 助手给出 2–3 个室内候选，并展示距离、预计停留和是否需要预约。
4. 小周选择其中一个，确认“用新活动替换原活动”。
5. 只有这一个时段变化；晚餐和演出保持不动。

**成功标准**：用户在一分钟内完成局部改动，不需要重新规划当天全部行程。

#### 旅程 D：预算收紧但保留必去点

**用户背景**：两位同行人发现花费偏高，仍想保留“故宫”和一顿特色晚餐。

1. 其中一人在行程规划页选择“更省钱”，并把故宫和晚餐标为“保留”。
2. 助手只针对未确认或可替换部分给出替代建议，如公交优先、免费景点、价格更低的餐食时段。
3. 结果区把“保留项”和“可调整项”分开展示，不把保留项再次作为候选。
4. 用户逐项勾选低预算替代方案；提交前看到“新增 1 项、替换 2 项、保留 2 项”。
5. 两位同行人确认后，行程同步为新的版本。

**成功标准**：预算调整可解释，用户知道哪些体验被保留、哪些是主动取舍。

#### 旅程 E：地点不确定时不强行导入

**用户背景**：用户输入“找一个有氛围的夜市逛逛”。

1. 助手不直接生成“夜市美食探索”这种无法导航的卡片。
2. 它给出具体地点候选；如果无法确认具体地点，改为说明“请选一个区域或查看地图候选”。
3. 用户选择地点后，再生成可导入的活动卡。

**成功标准**：行程里不会出现无法导航、无法判断在哪里的泛化活动。

### 4.6 行程规划验收标准

- 用户进入后能看到旅行摘要、快捷条件和示例输入，不必重新填写既有旅行信息。
- 用户可通过文本、图片或两者组合表达需求；失败后输入、图片和已选条件仍可继续使用。
- 首次可生成时，结果必须以可勾选的日程卡和按日工作台呈现，而非仅一段文字。
- 每张活动/酒店候选都清楚显示地点状态；地点不明确时不得默认加入。
- 用户可对某一天或时段提出局部调整；系统在任何替换、移动、删除前说明影响范围并要求确认。
- 用户确认前不改动行程；确认后仅写入勾选项目，其他草稿不会对同行人可见。

## 5. 攻略整理与单卡录入

用户粘贴公开攻略链接时，助手将标题、地点、图片和摘要预填为一张待编辑卡片。用户仍需确认时间、价格、地点等信息后保存。

当用户只想补一张活动、酒店或航班卡时，助手通过简短补问收集缺失信息。页面明确列出缺什么，并在完整前不显示“确认保存”。

**典型案例**：用户说“周五晚上从东京飞大阪，航班号 JL123”。助手补问起降机场与起飞时间；用户补齐后预填航班卡。用户仍可以修改价格、备注和链接再保存。

## 6. 支出录入

用户可拍摄小票或输入“午餐炒饭 25 人民币”。助手生成金额、类别、日期和备注草案；用户预览时可以修正金额、选择关联行程卡，再确认保存。

**典型案例**：用户上传模糊小票，助手只识别出“餐饮”和日期，金额标为待补充。用户手工输入金额后，才可保存。识别不完整不妨碍用户完成记账。

## 7. 卡包识别

用户拍摄银行卡、门票、证件或会员卡后，助手将识别结果预填到编辑页。用户检查、修改并保存；卡片默认遮挡，复制敏感号码前会再次提醒。

**典型案例**：用户拍摄一张门票，助手识别出“东京塔门票”和编号，但不确定有效期。用户补充备注后保存；无法识别时，用户仍可直接手工创建卡片。

## 8. 明日备忘

助手根据次日行程提出三类建议：起床/出发闹钟、待办提醒、行李或随身物品。每条建议都可单独添加，也可一次添加全部；已添加项要有明确状态，避免重复写入。

**典型案例**：明天 08:30 有航班、14:00 入住酒店。助手建议 05:30 起床闹钟、今晚确认证件和充电宝的提醒、随身携带护照和转换插头。用户只添加闹钟和证件提醒，不添加物品建议。

## 9. 运营指标

- 行程规划：打开后发起率、首次生成成功率、候选卡选中率、加入行程率、局部调整率。
- 攻略整理：链接导入成功率、预填后保存率。
- 支出录入：草案完整率、人工修改率、确认保存率。
- 卡包识别：识别后保存率、识别失败后的手工保存率。
- 明日备忘：建议生成率、各类建议的单条添加率、全部添加率。

指标只用于评估功能效果，不记录用户的行程正文、图片、号码或证件内容。
